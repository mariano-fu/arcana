# Plan — Technical design

## Architecture at a glance

```
 iPhone (installed PWA)          Laptop (browser / installed PWA)
 ┌──────────────────────┐        ┌──────────────────────┐
 │ React + TS UI        │        │ same app             │
 │ Dexie (IndexedDB)  ◄─┼─ UI reads/writes local only    │
 │ Sync engine          │        │                      │
 │ Service worker cache │        │                      │
 └─────────┬────────────┘        └──────────┬───────────┘
           │ HTTPS, when online (push/pull)  │
           ▼                                 ▼
 ┌──────────────────────────────────────────────────────┐
 │ Homelab (Docker Compose)                             │
 │ Caddy ─ serves PWA static files + proxies /api       │
 │ Django + DRF (gunicorn) ── PostgreSQL                │
 │ Scheduled job: daily horoscopes (provider adapters)  │
 └──────────────────────────────────────────────────────┘
   reachable only inside the tailnet via `tailscale serve`
   (https://<host>.<tailnet>.ts.net, no public exposure)
```

**Key decision:** the UI never calls the API directly for data. It only talks to IndexedDB. A separate sync engine reconciles IndexedDB with the server in the background. This is what makes offline "free" and is the main architecture story for the README.

## Data model

All synced tables share these columns:

| Column | Type | Notes |
|---|---|---|
| `id` | UUID (v7, generated on the client) | Lets devices create records offline without collisions. The exceptions are seed rows (see "Seed vs. user edits") and `card_draw` (see below) |
| `updated_at` | timestamptz (client clock) | Used for last-write-wins |
| `deleted_at` | timestamptz null | Tombstone |
| `server_version` | bigint | Server-assigned from a global sequence on every write; pull cursor |
| `device_id` | UUID | Which device last wrote it (debugging, conflict UI) |

Local-only (IndexedDB, never sent to the server):
- `pending` (`0|1`, not boolean, because IndexedDB can't index booleans): 1 while a row has unsynced changes. The sync push reads `where('pending').equals(1)`, tombstones included.
- `meta` key/value table: `device_id` (UUIDv7 created on first run), `seed_version:spreads` and `seed_version:crystals` (the bundled `version` last loaded, see "Seed vs. user edits"), `app:build` (the build that last started, T4.7), `fresh_session:<id>` (a session just created by "Nueva sesión": its fields as created, its `updated_at`, and whether creating it unarchived the client; read and removed by the discard-on-leave check and the startup sweep in `features/sessions/actions.ts`), later the sync cursor.

Local conventions: field names stay snake_case so rows go to the sync API as-is; timestamps are ISO 8601 UTC strings (sort lexically, which last-write-wins relies on); `server_version` is null until first sync. Deletes are soft (`deleted_at` set, row re-stamped `pending`), and repository reads hide tombstones by default.

Tables:
- **client**: name, instagram, whatsapp, email, birth_date (date, null), birth_time (time, null), birth_place_label, birth_lat, birth_lng, birth_tz (IANA), notes, tags (text[]), archived (bool), created_at
- **session**: client_id, started_at, type (`in_person|online|message`), price_minor (int, null — céntimos/cents), currency (`CRC|USD`, default `CRC`), notes, follow_up_note, follow_up_date
- **payment**: session_id, client_id (denormalized for fast per-client totals), amount_minor (int), currency (`CRC|USD`), method (`sinpe|cash|transfer|paypal|other`), paid_at (date), reference (text, null — e.g. SINPE receipt number), note. Session status (`paid|partial|pending|no_charge|overpaid`) is **derived**, never stored, so it can't drift out of sync; a `paymentStatus(session, payments)` pure function owns that logic and is unit-tested.
- **reading**: session_id, spread_template_id, spread_snapshot, label, created_at. `spread_snapshot` (JSON: `{name, positions: [{index, name, meaning, layout}]}`, with `layout` as in `spread_template`, so past readings can redraw the spread's shape without the template) is a copy of the spread taken when the reading is created and never changed afterwards. Past readings always display from the snapshot, never from the current `spread_template`, so seed updates and her edits to custom spreads can't rewrite history. `spread_template_id` stays only as a reference (e.g. "readings with this spread") and may point to a template that has since changed or been deleted.
- **card_draw**: reading_id, position_index (1-based, matches `index` in the reading's `spread_snapshot.positions`), card_id (seed key, e.g. `major-00`, `cups-07`), reversed (bool), note. card_draw ids are UUIDv5 of `card_draw:<reading_id>:<position_index>`, so each position has at most one draw row across devices (exception to UUIDv7). Removing a card tombstones that row; placing a card there again revives it, keeping its note.
- **spread_template**: name, description (when to use it and how to read it; may be empty for custom spreads), positions (JSON: `[{index, name, meaning, layout}]`), is_seed, seed_key. `index` is the 1-based position number shown to her. Position numbers are 1-based everywhere: template positions, `reading.spread_snapshot.positions[].index` and `card_draw.position_index`. `layout` is `{col, row, rotated}` (0-based grid cell; `rotated` lays the card crosswise, e.g. the Cruz Celta's Desafío over card 1) or null for a custom spread without placement. Seed spreads are read-only; to change one she copies it into a custom spread (`is_seed = false`, `seed_key = null`). Custom spreads (builder, T1.10): 1–20 positions, numbered 1..N in list order on save; `meaning` and `description` may be empty; positions may mix a layout and `null`. Layouts follow the same rules as the seed (`spreadLayoutIssues` in `seed/spreads.ts`): inside the 7×5 grid (`SPREAD_GRID`), at most one upright and one crosswise card per cell, a crosswise card only over an upright one. Names are unique among live spreads, seed and custom, compared trimmed and case- and accent-insensitive; "Duplicar" names copies "<nombre> (copia)", "(copia 2)"… with the first free number.
- **crystal**: seed_key (null if user-created), name, colors, chakras, signs, intentions (tag keys), description, care, hidden, user_modified (bool). No inventory fields in v1. Future inventory goes in a separate `crystal_stock` table (crystal_id, quantity, cost_minor, price_minor, currency), so recommendations never depend on stock data.
- **intention_tag**: key, label (null for a seed tag she hasn't renamed: the UI shows the `es.json` label for the key, `crystals.intention.*`; her own tags and seed tags she renamed store a real label)
- **card_note**: card_id, note (her personal notes per card). At most one row per card: its id is UUIDv5 of `card_note:<card_id>` (exception to UUIDv7, like `card_draw`), so notes written on two devices merge into one row; a blank note tombstones it and writing again revives it.
- **conflict**: table, record_id, field, losing_value, losing_device_id, created_at, resolved (bool)
- **horoscope** (server-owned, read-only on clients): date, sign, period (`day`), text_en, text_es, source, translator

Seed-only (bundled JSON, not synced, versioned): tarot cards, zodiac sign profiles, cities.

Tarot cards (`seed/cards.es.json`, schema in `seed/cards.ts`): key, arcana, number, suit, element, astrology (Golden Dawn), keywords, upright, reversed. Majors store their Spanish `name`. Minor names are not stored: they are built from the rank and suit labels in `es.json` (`cards.rank.*`, `cards.suit.*`, e.g. "Paje de Oros"), so renaming a suit or court rank is a one-line edit. Court ranks are numbered 11 Paje, 12 Caballero, 13 Reina, 14 Rey; the Ace is 1. Astrology (recorded in the seed's `astrology_system` field): attributions follow the Golden Dawn (Book T) system: decans for pips 2–10; courts use the "20° to 20°" ranges, with GD Knight → RWS Rey and GD Prince → RWS Caballero. ‘Elemento’ on the majors is the sign’s element for zodiac cards and ‘—’ for planet cards. The exceptions follow GD’s own elemental attributions: the three elemental trumps El Loco (Aire), El Colgado (Agua) and El Juicio (Fuego), and El Mundo (Saturno + Tierra). Uranus, Neptune and Pluto are deliberately left out (modern additions, not original GD). Meanings are gender-neutral toward the consultant (a test rejects common masculine-only words, with an allowlist). `docs/review/cards-es.md` is generated from the seed (`npm run build:cards-review`) for her review, and a test fails if it is stale.

Spreads (`seed/spreads.json`, schema in `seed/spreads.ts`): key, name, description, positions with layout (see `spread_template`). The seed holds the four agreed spreads: 1 carta, 3 cartas (pasado/presente/futuro), Herradura (7: pasado, presente, futuro próximo, consejo, entorno, esperanzas y temores, resultado) and Cruz Celta (10, modern order: 3 Base, 5 Corona, 7 La persona consultante). Descriptions and position meanings are written for a reader who is learning: when to use the spread, what to look for in each position. Texts pass the same gender-neutral check as the cards (shared helper in `src/test/gender-neutral.ts`). `docs/review/spreads-es.md` is generated (`npm run build:spreads-review`), with a text sketch of each layout, and a test fails if it is stale.

Zodiac (`seed/zodiac.es.json`, schema in `seed/zodiac.ts`): 12 signs in zodiac order with key (English, e.g. `scorpio`; crystals reference these), number, Spanish name, glyph, `start`/`end` (`{month, day}`, inclusive standard date table, Capricornio wraps the year; display only, `sunSign` never uses it), element, modality (`cardinal|fixed|mutable`), `ruler` (modern: Plutón, Urano, Neptuno for Escorpio, Acuario, Piscis) and `traditional_ruler` (classical seven only), traits (nouns, so they stay gender-neutral), description (strengths and shadow) and `compatible` (same element plus the complementary one: fire ↔ air, earth ↔ water; symmetric, 5 signs each) and `challenging` (the two square signs: same modality, three signs away, element neither its own nor the complementary one, e.g. Aries → Cáncer, Capricornio; symmetric, never also compatible). Planet and modality labels live in `es.json` (`astro.planet.*`, `zodiac.modality.*`, `zodiac.field.challenging` = "Signos desafiantes"). Texts (name, traits, description) pass the gender-neutral and health-claim checks.

Crystals (`seed/crystals.es.json`, schema in `seed/crystals.ts`): about 50 commonly recommended crystals, recommendation-only (no stock, price or quantity fields; the schema is strict, so they fail validation). Each has key (English kebab-case, e.g. `rose-quartz`; matches `crystal.seed_key`), Spanish name, colors, chakras, signs (zodiac seed keys), intentions, description and care (cleansing, plus water or sun sensitivity). Colors, chakras (the 7 main ones: `root, sacral, solarPlexus, heart, throat, thirdEye, crown`) and intentions are key enums with Spanish labels in `es.json` (`crystals.color.*`, `crystals.chakra.*`, `crystals.intention.*`). Intention keys name what the person seeks (`calm`, `rest`, `abundance`, `confidence`…), never a problem; T1.6 seeds an `intention_tag` row per key, with `label: null` (see `intention_tag`). Every sign has ≥ 3 crystals, every chakra ≥ 2 and every intention ≥ 3, so the recommender always has candidates. Descriptions frame associations and traditional uses ("se asocia con…", "tradicionalmente se usa para…"); a test rejects health-claim words (shared helper `src/test/health-claims.ts`: cura, sana, trata, alivia, enfermedad…) and the texts pass the gender-neutral check. `docs/review/crystals-es.md` is generated (`npm run build:crystals-review`), listing the intention tags first, and a test fails if it is stale.

Recommender (`features/crystals/recommend.ts`, pure): `clientSigns(client)` (`astro/clientSigns.ts`) gives the sun (from the date alone unless time and timezone are known; on a cusp date, both signs), the Moon (needs the timezone; without a birth time it is left out and marked uncertain when it changes sign that local day) and the rising sign (needs time and coordinates). Score = sun 2 + moon 1 + rising 1 (placements add up) + 3 per chosen intention; each sign or intention counts once per crystal. On a cusp date either sun sign earns the 2 points, once, with the reason marked "posible". Hidden crystals, tombstones and score 0 are left out; her edited and own crystals are scored from their rows; a chosen intention counts only while its tag exists. Reasons are data, worded via `crystals.reason.*` ("Sol en Leo · Luna en Leo · Intenciones: Calma, Protección"). The cusp, uncertain-Moon, limit, deleted-tag and tie rules (T2.8 decisions 1–7) were confirmed by Mariano on 2026-10-21. On client detail (`features/crystals/CrystalRecommendations.tsx`, T2.9 part 1): intention chips (live tags, her labels, alphabetical), none chosen by default and never saved; the top 5, then 5 more per "Ver más"; with no birth date and no intention chosen it shows only "Agregue fecha de nacimiento o elija una intención" (T2.9 Q1, Q2, Q6, confirmed by Mariano on 2026-10-24).

### Seed vs. user edits (Principle 5)
On app start (`seed/loader.ts`, `loadSeed`), compare each bundled seed's `version` with the one stored in `meta` (`seed_version:spreads`, `seed_version:crystals`; intention tags follow the crystals version) and load only the seeds that differ, in one transaction, so running it twice or from two tabs is safe.
- **Ids:** seed rows are the one exception to UUIDv7 ids. Their id is a UUIDv5 of `"<table>:<seed_key>"` under a fixed namespace (`SEED_ID_NAMESPACE`, never changed), so every device creates the same rows and syncing never duplicates them; `reading.spread_template_id` points to the same spread everywhere.
- **Not synced by default:** the loader writes seed rows with `pending = 0`, because each device derives them from its own bundle. Only her edits (made through the repositories, `pending = 1`) sync. Rows that already exist keep their `pending` and `server_version`.
- **Crystals:** insert new seed rows; update existing seed rows **only if `user_modified = false`**, and then only the seed content (name, colors, chakras, signs, intentions, description, care), never `hidden`. Never touch her own crystals (`seed_key = null`).
- **Spreads:** seed spreads are read-only in the app, so seed rows are always updated to the bundled version (no `user_modified` flag); her custom spreads (`is_seed = false`) are never touched, and copies she made of a seed spread are independent custom rows.
  Open issue: future seed spreads could reuse a custom spread's name; decide a rule before adding any new seed spread.
- **Intention tags:** add-only. A seed key with no row (looked up by `key`) gets one with `label: null`; existing rows, renamed or not, are never updated.
- **Deletes:** a seed row she deleted (tombstone) stays deleted, and rows dropped from a newer seed are kept. The loader never deletes anything.

## Sync protocol

Single endpoint, push-then-pull, idempotent.

```
POST /api/sync/
{
  "device_id": "…",
  "cursor": 1842,              // last server_version this device has seen
  "changes": [                 // local rows with pending=true
    { "table": "client", "record": { …full row… } }
  ]
}
→ 200
{
  "results":   [{ "table": "client", "id": "…", "status": "applied" }, …],  // one per pushed record, in order
  "conflicts": [{ "table": "client", "id": "…", "field": "notes" }],
  "changes":   [ { "table": …, "record": … } ],   // server_version > cursor, excluding rows this request just wrote
  "cursor":    1907,
  "server_time": "2026-10-19T12:00:00.000Z",
  "epoch":     "…"               // random id of the server's database
}
```

Single tenant: the server holds one practice's data. Any authenticated account syncs that one dataset; rows have no owner column. Multi-user is out of scope.

Server rules per incoming record:
1. If no existing row → insert, assign `server_version`.
2. If incoming `updated_at` > stored `updated_at` → overwrite. For free-text fields (`notes`, `follow_up_note`, `card_draw.note`, `card_note.note`, `payment.note`): if the stored value differs and was written by a different device since this device's cursor, store the losing value in `conflict`.
3. If incoming is older → reject that record, return the server's version in `changes` (even if it is at or below the cursor). Equal `updated_at`: from the same device, or with content identical to the stored row (a pulled row echoed back, e.g. a server-created conflict), it is the same write again and counts as a `noop` (nothing written); otherwise the server's row wins. A rejected record's free-text fields get the same conflict check as rule 2, with the incoming value as the loser, so a device never silently loses text it typed.
4. Tombstones follow the same rules; a delete wins over an older edit. A child pushed for a tombstoned parent (a session for a deleted client) is accepted; the parent stays tombstoned and both are pulled (T3.7 surfaces it).

Details:
- **Conflict rows** are created by the server (`device_id` = nil UUID, `resolved = false`) with a deterministic id: UUIDv5 of `"<table>:<record_id>:<field>:<losing_updated_at>:<losing_device_id>"` under a fixed namespace (`CONFLICT_ID_NAMESPACE` in `sync/service.py`, never changed), inserted only if absent (a tombstoned one counts as present). A retried push therefore never duplicates or reopens a conflict, and one already resolved (resolved or tombstoned) is not reported again. Conflict rows detected by a push come back in that push's `changes`, along with `conflicts: [{table, id, field}]`.
- **Wire format:** records are full rows with model field names; foreign keys travel as `<name>_id`. Pulled records include `server_version`; incoming `server_version` is ignored and `device_id` is taken from the request, not the record. Timestamps are sent as `YYYY-MM-DDTHH:MM:SS.sssZ` (JS `toISOString()`). Times (`birth_time`) travel as `HH:MM`. Everything is millisecond precision: incoming timestamps are truncated to ms before any comparison, and every timestamp the server generates (`updated_at`/`created_at` on rows it writes, `server_time`) is truncated too.
- **Pull:** rows with `server_version > cursor` from every table, ordered, at most 500. Rows this request wrote are left out but still advance `cursor` (the last `server_version` in the page, or the request's cursor if the page is empty).
- **Push results:** `results` has one entry per pushed record, in request order: `applied` (written, rules 1–2), `noop` (equal `updated_at`, same write again, rule 3) or `rejected` (older, or equal and the server won, rule 3; the server's row is in `changes`). It is the client's only source for what happened to its push.
- **Rejected pushes:** a push is applied all or nothing. Any bad record → `400`, nothing applied, `{records: [{index, table, id, code, detail}]}` with `code` one of `invalid`, `server_owned` (pushes to `horoscope`), `clock_ahead` (`updated_at` more than 24 h after server time), `constraint`, `missing_parent` (foreign key to a row that exists neither on the server nor in the push). Malformed requests (unknown table, more than 500 changes) → `400` with DRF field errors. Request bodies may be up to 10 MB (`DATA_UPLOAD_MAX_MEMORY_SIZE`).
- **One writer at a time:** every write to a synced table goes through `synced_write()` (`sync/models.py`): a transaction holding a Postgres advisory lock, in which `SyncedModel.save()` takes the next `server_version`. The sync view runs push and pull in one such transaction, and the admin, the horoscope job and management commands write through `save()` too. Without it, a transaction that took a lower `server_version` could commit after a pull read a higher one, and the cursor would skip that row. Bulk queryset writes (`update`, `bulk_update`, `bulk_create`) on synced models raise, since they bypass `save()`.
- **Epoch:** a random UUID created once per database (`sync_epoch` table, one row, made by its migration) and returned in every sync response. Cursors are only meaningful within one epoch: a new database (reset, or a restore from an older backup) restarts `server_version`. The restored row carries the old epoch, so the restore script runs `manage.py rotate_sync_epoch` after restoring (T4.3) and devices notice.
- **No hard deletes:** `delete()` on a synced row or queryset raises, because a deleted row never reaches a pull. Deletes are tombstones; the admin has no delete permission and offers a "tombstone" action instead (`SyncedModel.tombstone()`: server clock, nil device). Every foreign key on or to a synced model is `PROTECT`, so no cascade can hard-delete synced rows (tested).

Client rules (`web/src/sync/`):
- **Local writes:** every local edit sets `pending = 1` and `updated_at = max(now, previous + 1 ms)`, strictly increasing per row even when the clock repeats a millisecond or is behind the stored version. A Dexie middleware (`db/monotonic.ts`) enforces it for every writer; writes with `pending = 0` (seed rows, pulled rows) are stored as given. The only exception is `writeVerbatim`, used by the sync engine for the epoch re-push and the clock_ahead re-stamp below, and by backup import (see "Export / import") so imported rows keep their real edit times.
- **Triggers:** app open; coming back to the foreground (`visibilitychange` → visible, at most once a minute: an installed iOS PWA usually resumes rather than reloads); the `online` event; every 5 min while visible; ~3 s after the last local edit (debounced); and "Sincronizar" (manual). Nothing relies on background sync, which iOS doesn't have.
- **One run at a time:** within a tab, a call during a run queues exactly one follow-up run; across tabs, runs hold the `arcana:sync` Web Lock (`navigator.locks`).
- **Push:** read every pending row (parents first: client, spread_template, crystal, intention_tag, card_note, session, payment, reading, card_draw, conflict), split into chunks of at most 500 rows or ~1 MB of JSON, whichever comes first (a single larger row goes alone). Each chunk is one request carrying the current cursor; its response is applied before the next chunk is sent, counting only that chunk's rows as pushed (a pulled copy of a row still waiting in a later chunk leaves it pending).
- **Pull:** then send empty requests until `cursor` stops advancing, at most 200 pages per run; a longer backlog ends the run as idle and the next run resumes from the saved cursor.
- **Applying a response** (one IndexedDB transaction with the cursor, so the cursor never gets ahead of its rows):
  - What happened to each pushed row comes only from `results`, never from which rows are in `changes`. A result for a row not in this chunk is ignored and logged.
  - `applied` / `noop`, row unchanged locally since it was read for the push → `pending = 0`. Edited meanwhile → stays pending; the next run pushes the new version.
  - `rejected`, row unchanged since the push → overwritten with that record's server row from `changes` (the losing text is already a conflict row on the server). Edited meanwhile → kept, pushed next.
  - Incoming row with no local row, or a local row that isn't pending → stored with `pending = 0` and its `server_version`.
  - Incoming row for any other pending local row (outside the push, or in it with `applied`/`noop`) → never overwrites it: the local edit is kept and the server decides on its push. Pulled rows are stored before `pending` is cleared, so this holds within the response too.
  - Tombstones, conflict rows and horoscopes are stored like any other row. Local `server_version` is only updated from pulled rows (pushed rows aren't echoed back); only the cursor drives pulls.
- **State** (`meta`): `sync:cursor`, `sync:epoch`, and `sync:status` (`idle`, `stopped`, `clock_ahead`, `session_expired`, `signed_out`, `offline`, `error`; last success; clock skew; the server's errors). "Syncing" is held in memory only.
- **Auth:** JWTs live in their own `auth` table, never in `meta` (so exporting `meta` can't leak them); `device_id` stays in `meta`. A 401 triggers one refresh and one retry. Refreshes hold the `arcana:auth` Web Lock and re-read the stored tokens first: if another tab already rotated them, its new access token is used instead of spending the blacklisted refresh token. A refused refresh (or a second 401) → `session_expired` ("Sesión expirada", log in again in Settings) and only the `auth` table is cleared: an auth failure never touches data, pending rows, the cursor or `device_id`.
- **A 400** is never retried automatically: `stopped` ("La sincronización está detenida", with the server's details), local data and pending rows kept. Automatic triggers skip while `stopped`, `clock_ahead` or `session_expired`; each tap on "Sincronizar" retries once.
- **clock_ahead** (a 400 for `updated_at` more than 24 h ahead): "Revise la fecha y hora del teléfono". On the manual retry, the flagged rows still pending and dated after the device's current time are re-stamped to now (`writeVerbatim`, so their `updated_at` ends up ≤ now); the server never accepted the future version, so nothing synced moves back.
- **Network error, 5xx, 429:** the run ends (`offline` / `error`); the next trigger tries again. No retry loop.
- **Epoch change:** if a response's `epoch` differs from the stored one, its page is not applied. The device resets the cursor to 0 and marks every row pending again, live and tombstoned, **keeping each `updated_at` unchanged** (`writeVerbatim`), so last-write-wins on the re-push compares the real edit times; then it re-pushes and pulls from 0. Seed rows never pushed and still as bundled are left out (each device has them from its bundle; pushing them would let an older bundle overwrite a newer one elsewhere). A device with no stored epoch adopts the first one it sees.
- **First sync** (no stored epoch and cursor 0): rows written before sync existed may have `pending = 0` without ever reaching the server (her iPhone's pre-sync data), so before pushing, every row is marked pending the same way as for an epoch change: live and tombstoned, `updated_at` unchanged (`writeVerbatim`), untouched seed rows left out. A seed row counts as edited, and is pushed whatever its `pending` flag says, if she changed it: `user_modified`, `hidden`, renamed (intention tags) or tombstoned. Hiding a crystal sets only `hidden`, not `user_modified`, so both are checked. The server's last-write-wins keeps her rows over any older server copy. Until a response stores the epoch, each run marks again, which is harmless.
- **App closed mid-sync:** before the response arrives, rows stay pending and are re-pushed next run; the server treats a same-device, same-`updated_at` row as a `noop` result, which clears `pending`, and conflict ids are deterministic, so nothing duplicates. During the apply transaction, IndexedDB rolls it back whole: rows and cursor as before. Between pages, the cursor is that of the last applied page.
- **Clock skew:** each response's `server_time` minus the midpoint of the request is stored; T3.8 shows a warning in Settings above 2 min.
- **Ajustes → Sincronización (T3.8):** below Respaldo. Signed out (no tokens in `auth`), it is one neutral line and an "Iniciar sesión" button that opens the form; no banner or badge anywhere. Signed in, it shows "Sesión iniciada", last sync, the pending-row count (until the first response stores an epoch, a line saying all data will be sent at the first sync instead, since rows from before sync are only marked then), the skew warning (signed in only), "Sincronizar" and "Cerrar sesión". `signOut()` waits for the `arcana:sync` lock, clears `auth` and the stored skew, and saves `signed_out`; data, pending rows, cursor and epoch stay. A successful login starts one manual run. Only a JSON response is the API's: a non-JSON body (an HTML page while no API is deployed) or a 404/5xx is a server error, so login says "No se pudo conectar con el servidor" and never "Usuario o contraseña incorrectos".
- **Hard deletes:** synced tables refuse `delete`, `bulkDelete`, `clear` and `Collection.delete` (`HardDeleteError`, in the `updated_at` middleware): a removed row never reaches a push. Deletes are tombstones. `meta`, `auth` and deleting the whole database (`db.delete()`, export/import) are unaffected.
- **Conflicts (T3.7, "Conflictos"):** open conflict rows (`!resolved`, not tombstoned) are grouped per field and counted, with orphaned sessions, on an Inicio card and a badge on the Inicio tab. Only free-text fields get conflicts; she keeps the current text, uses another version, or combines them in an editor prefilled with the current text then the others. A field that isn't free text (never sent today) only keeps the current value. Resolving is one local transaction: the record (for "use" or "combine") and every conflict row of the field, the conflict rows marked `resolved` and tombstoned, all `pending = 1` through the `updated_at` middleware, so the resolution beats the server-created row even from a device whose clock is behind. A conflict whose row was deleted offers copy and discard only; one whose row hasn't synced to the device yet waits.
- **Orphans (T3.7):** a live session whose client is tombstoned shows as "Sesión de una ficha eliminada": restore the ficha (only the ficha; its other deleted sessions stay deleted) or delete the session (the usual cascade). Open issue: payments, readings and card draws under a deleted session aren't surfaced yet (v1 covers sessions only).

Tests must cover: concurrent edits on two devices, delete vs. edit, offline for a week then sync, notes conflict preserved, re-sending the same push twice (idempotent).

## Export / import (T1.13)

`features/backup/`, in Ajustes → Respaldo. Constitution §2: works with no server. D1–D7 confirmed by Mariano (2026-10-24).

- **File** (`arcana-respaldo-YYYY-MM-DD.json`, local date): `format: "arcana-backup"`, `format_version`, `db_schema_version` (Dexie `verno`), `app_version`, `exported_at`, the exporting `device_id` and `seed_versions` (informational), and `tables`: every row of the ten tables sync pushes, live and tombstoned, as stored minus `pending`. Never in it: the `auth` table, `sync:*` (cursor, epoch, status), this device's `device_id` and seed versions as data, `fresh_session:*`, and horoscopes (server-owned, refetchable; D2).
- **Format versions:** any change to a row's fields (added, removed or retyped) bumps `format_version` and adds a migration step from the previous version (`MIGRATIONS` in `features/backup/format.ts`). The Zod row schemas are tied to `db/types.ts` by a type-level test, and the current version's field signature is committed as `formats/v<N>.json`; a schema change without a bump fails the tests. A newer version is refused ("Este respaldo se hizo con una versión más nueva de la app…"), as is an unknown one.
- **Export:** one tap. The backup is read ahead by a live query, so the tap only stamps the date, serializes and runs the import validator on the result (Zod, duplicate ids, foreign keys within the file). If that fails, she sees an error instead of the share sheet. Then `saveTextFile`, as for the CSV: share sheet where files can be shared, download otherwise.
- **Import** merges; there is no replace mode (D1). The file is validated whole first (strict Zod schemas, ≤ 25 MB (D5), no duplicate ids); a preview shows what would change, and nothing is written until she confirms (D4). Then one `writeVerbatim` transaction decides every row against the stored rows again, checks foreign keys (each parent in the file or on the device, tombstones included: an orphan would stop sync with `missing_parent`), and writes. Any failure rolls it all back. The counts she sees come from that transaction.
- **Merge rule per row** (ids kept, so never duplicated): no local row → stored; newer `updated_at` → overwrites; older → the local row stays; equal with identical content (ignoring `pending`, `server_version`, `device_id`) → skipped; equal with different content → the local row stays, as the server keeps the stored row on a tie (D3). Tombstones are rows like any other. A conflict copy resolved on the device stays resolved against an older backup. When an import overwrites a pending local row, each free-text field (as in sync rule 2) whose local value differs becomes a conflict row with the local value as the loser, under the same deterministic id, inserted only if absent; a synced local row is overwritten without one (D6).
- **Seed rows:** untouched seed rows in the file (`isUntouchedSeedRow`) are skipped: this device's bundle owns them. An edited seed row (`user_modified`, `hidden`, renamed tag, tombstone) always replaces an untouched local one, whose `updated_at` is only the loader's stamp; between two edited rows the normal rule applies. Seed versions are never imported; the loader's rules keep imported edits on later seed updates.
- **Sync:** written rows keep `updated_at`/`deleted_at` exactly as in the file and get `pending = 1`; `server_version` stays the local row's, or the file's for a new row. The server's last-write-wins has the last word on the push, so an old backup can't roll the server back. Cursor, epoch and `device_id` are untouched. Rows dated more than 24 h ahead are imported with a preview warning ("Algunos registros tienen una fecha futura; revise la fecha y hora del teléfono."); the `clock_ahead` re-stamp handles their push. After an import, one sync run is requested.
- **Privacy:** the file is plain JSON with client data, like the CSV (no encryption, D7); Ajustes tells her to keep it somewhere private.

## Astrology module (`web/src/astro/`)

Pure functions, no UI:
- `sunSign(birthDate, utc?)` → always from the Sun's ecliptic longitude (astronomy-engine), never from the date table (which is only for displaying ranges). With `utc` (time and place known, via `toUtc`): the sign at that instant. Date-only: compute the longitude at the day's two extreme instants (its start in UTC+14 and its end in UTC−12); same sign → `cusp: false`; different → `cusp: true`, primary sign = the sign at 12:00 UTC that day, `alternative` = the other.
- `toUtc(date, time | null, ianaTz)` → Luxon; when time is null, use 12:00 local and mark result `timeKnown: false`. A local time inside a DST gap (never existed) is shifted forward by the gap; a local time that occurred twice resolves to the earlier instant. The result's `adjusted` (`'none' | 'gap' | 'ambiguous'`) says which rule applied.
- `planetPositions(utc)` → sun, moon, mercury … pluto geocentric apparent longitudes on the true ecliptic of date via astronomy-engine → `{ longitude, sign, degree }` per planet (`degree` within the sign, 0–30).
- `moonSignsOnLocalDay(date, tz)` → the Moon's sign at the start and end of that local day (from its first local instant per `toUtc` to the next day's); `moonSignUncertain(date, tz)` is true when they differ.
- `splitPosition(longitude)` / `formatPosition(longitude)` (`astro/format.ts`) → the one way positions are displayed: degrees and arc-minutes within the sign, flooring total arc-minutes and never above 29°59′ (89.713° is `29°42′ Géminis`, not 29°43′); the sign always matches `signForLongitude`.
- `ascendantAndHouses(utc, lat, lng)` → only when time known; Placidus (confirmed as her system), whole-sign as fallback where Placidus is undefined: |lat| ≥ 90° − true obliquity of date (≈ 66.56°), or if a cusp's semi-arc cannot be solved. Returns `{ system: 'placidus' | 'whole-sign', ascendant, mc, cusps }` (each `{ longitude, sign, degree }`, cusps for houses 1–12); the ascendant and MC are always computed, and under whole-sign the MC is reported as a point, not the 10th cusp.
- Zodiac: Western tropical (confirmed). No sidereal support needed.

Reference test set: 10+ charts with known positions (pick public charts and verify against a trusted online ephemeris). Tolerance 1°. Planet positions are checked against NASA JPL Horizons (DE441, geocentric, `QUANTITIES='31'`): `astro/fixtures/horizons-reference.json` records the source and query, and `npm run fetch:horizons-reference` regenerates it (needs network, never run in CI). Ascendant, MC and Placidus cusps are checked against `astro/fixtures/houses-reference.json`: values only, generated once outside the repo with Swiss Ephemeris (pyswisseph `swe_houses`, 'P'), tolerance 0.01°; its `source` block records the version and call. No Swiss Ephemeris code or script in the repo (AGPL). Cases include Costa Rica (incl. a DST year), the Southern hemisphere and Tromsø (whole-sign fallback; only Asc/MC compared).

Cities (`seed/cities.json`, generated by `npm run build:cities` from `web/scripts/build-cities.ts`; rules in `web/scripts/cities.ts`): GeoNames (CC BY 4.0, credited on the "Acerca de" screen). Central America (BZ, GT, SV, HN, NI, CR, PA) from `cities1000`; the rest of Latin America (MX, CU, DO, HT, PR and South America), Spain, the US and Canada from `cities15000`; elsewhere, national capitals (PPLC) from `cities15000`. Historical, abandoned and destroyed places are excluded. Fields: `name, label, country, lat, lng, tz` and optional `alt`; sorted by population, coordinates rounded to 4 decimals.
- City names: the Spanish preferred alternate name (isolanguage `es` and isPreferredName = 1) → first Spanish name → GeoNames name ("Londres", "Nueva York"). Costa Rica always uses the GeoNames name ("Limón", "San Isidro"); the canton tells repeats apart. The GeoNames name and all other Spanish names stay searchable (`alt`, a list).
- Province/canton names (admin1/admin2, via `admin1CodesASCII.txt`/`admin2Codes.txt`): preferred `es` name → first `es` name → GeoNames name, then a fixed list of administrative prefixes and suffixes is stripped ("Provincia de", "Cantón de", "Estado", " Province", …; matched ignoring case), except where the prefix is part of the name ("Distrito de Columbia").
- Country names: `Intl.DisplayNames` es-CR, resolved at build time and baked into the labels.
- Labels (unique; this is what `birth_place_label` stores): Costa Rica is city, canton (admin2), province, with no country ("San Rafael, Escazú, San José"). Latin America, Spain and the US: city, admin1, country. Elsewhere: city, country, plus admin1 when another entry in the same country has the same city name ("Portland, Oregón, Estados Unidos"). Consecutive repeated parts collapse ("San José, San José, San José" → "San José").
- Collision rule (for future GeoNames updates): if labels still clash, add the next admin level (admin2) to every entry in the clash; if that does not separate them, keep one entry: a populated place over a section of one (PPLX, e.g. a neighbourhood), then the most populous; drop the rest. The build prints every resolution, and a test requires unique labels.
- Size: the lazily loaded `cities-*.js` chunk must be in the service worker precache and under Workbox's 2 MiB per-file limit (`npm run build` fails otherwise, via `scripts/check-precache.ts`); target < 1 MB gzipped.
- Client form: offline autocomplete (max 8 suggestions; accent-insensitive; within each match rank Costa Rican places come first, then by population, so "San José" finds hers before San José, California). Picking a city fills `birth_place_label`, `birth_lat`, `birth_lng`, `birth_tz`; editing the text afterwards clears the coordinates. Manual fallback: latitude, longitude and an IANA timezone, all three or none. Older clients with a label but no coordinates keep the label and show "sin coordenadas".

## Deploy (`deploy/`)

Docker Compose on the homelab (`deploy/docker-compose.yml`, run from `deploy/` with `deploy/.env`, gitignored; `deploy/.env.example` lists every variable with placeholders).

- **Services:** `db` (Postgres 16), a one-shot `migrate` (`manage.py migrate` on every `up`, simplejwt's blacklist tables included; `api` and `cron` start only after it succeeds), `api` (gunicorn), `cron` (supercronic: `flushexpiredtokens` daily at 03:30 Costa Rica time, `deploy/crontab`) and `caddy`. Start order: `db` healthy → `migrate` completed → `api`, `cron`. `caddy` depends on nothing: it resolves `api:8000` per request, so the app shell is served even if the API never starts (for example after a failed migration), and `/api` answers 502 until it does.
- **PWA build:** the `caddy` image builds the PWA in a Node stage (`npm ci && npm run build`, licence check included). The build context has no `.git`, so the commit shown in Ajustes → Versiones comes from the `BUILD_COMMIT` build arg (`BUILD_COMMIT=$(git rev-parse --short=7 HEAD) docker compose up -d --build`); unset, it shows "dev".
- **Proxy chain:** device → `tailscale serve` on the host (TLS, ts.net certificate; sets `X-Forwarded-For` to the device's tailnet address and `X-Forwarded-Proto: https`) → Caddy, published on the host's loopback only (`127.0.0.1:8080`) → gunicorn. Caddy sees tailscale's connection from Docker's bridge gateway, a private address, and trusts `private_ranges` (`trusted_proxies`, strict, right to left): it keeps tailscale's headers and appends that address, so `X-Forwarded-For` reaches Django as `<device>, <gateway>` and `NUM_PROXIES = 2` picks the device. Tailnet addresses (100.64.0.0/10) are not private ranges, so a device can't pose as a proxy, and a client-sent `X-Forwarded-For` only adds entries to the left. Caddy's access log shows `client_ip` = the device.
- **Single origin:** Caddy serves the PWA and proxies `/api/*` on the same host; no CORS. `/admin` is not proxied (v1). The api publishes no port; for an admin session an opt-in `admin` service (compose profile `admin`, a second api process on `127.0.0.1:8001`) is started, reached over an SSH tunnel and stopped afterwards, because requests to it bypass Caddy's limits and the proxy chain. One-off commands use `docker compose exec`.
- **Caching:** hashed files (`/assets/*`, `/workbox-*.js`) are `public, max-age=31536000, immutable` and a missing one is a 404, never the app shell. Everything else (`index.html`, `sw.js`, `registerSW.js`, the manifest, icons) is `no-cache` (revalidated with ETags on every load). SPA routes fall back to `index.html`. `/api/*` responses are `no-store`. `.webmanifest` is served as `application/manifest+json`. Responses are compressed (`encode zstd gzip`).
- **Request limits:** a sync push is at most 500 records (`PUSH_LIMIT`) and 10 MB (`DATA_UPLOAD_MAX_MEMORY_SIZE`); the client splits pushes at ~1 MB. Caddy refuses `/api` bodies over 11 MB and buffers them before proxying, so a slow upload never holds a worker. gunicorn: 2 sync workers (`WEB_CONCURRENCY`; each keeps its own throttle counts, so the effective auth limit is the rate times the workers), `--timeout 60` (a request running longer restarts its worker), `--graceful-timeout 30`.
- **Data:** the database lives in an external, fixed-name volume (`arcana_pgdata`, created once with `docker volume create`), which `docker compose down -v` can't remove. Backups: T4.3.
- **Secrets** reach the containers only through `deploy/.env` (`env_file`, compose interpolation), never baked into an image; compose refuses to start without `SECRET_KEY` and `POSTGRES_PASSWORD`.
- **Hardening:** every service but `db` runs as a non-root user (api/cron uid 10001, caddy 10002) with a read-only root filesystem, all capabilities dropped and `no-new-privileges`. `db` starts as root (the official entrypoint prepares the data directory) and runs Postgres as `postgres`; it sits only on an internal network with no route out. Base images are pinned by tag and digest, supercronic by version and SHA-256.
- **Checks:** `deploy/smoke.sh` brings the stack up under its own project name and volume and checks all of the above from the host, as tailscale serve reaches it (CI `deploy` job, not required).

## Security
